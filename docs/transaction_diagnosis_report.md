# STEP16 
# 트랜잭션 처리의 한계와 대응 방안 설계 보고서

## 1. 배경 (모놀리식 아키텍처 > msa 아키텍처)
   - 사용량 증가에 따라 대용량 트래픽을 감당하는데 한계가 있습니다.
   - 특정 도메인의 장애/배포가 전체 시스템에 영향을 주게 됩니다.
   - 도메인 별로 독립적인 확장이 불가능 합니다(ex.주문의 경우 쿠폰에 비해 더 큰 scale-out이 필요함)
   -> 이에 따라  어플리케이션 서버와 DB를 도메인별로 분리할 수 밖에 없는 지점이 발생합니다. 

## 2. 한계 및 발생가능 문제
- 기존 모놀리식 아키텍쳐에서는 단일 서버에서 트랜잭션을 관리하기 때문에 일관성을 보장할 수 있었습니다. 그러나 MSA전환 후 각 서비스가 독립적인 DB를 사용하기 때문에 단일 트랜잭션으로 묶어서 사용할 수 없게 되었습니다.
- 이에 따라 주문 > 재고 > 결제 도메인이 분리되고 주문 서비스 성공 / 재고 서비스 성공 / 결제 서비스 실패인 부분 실패 시나리오가 발생하게 됩니다.
> 모든 도메인에 대하여 일관성이 보장되도록, 즉 최종 일관성(Eventual Consistency)을 보장하도록 변경이 필요합니다. 이에 따라 트랜잭션이 분리되더라도 일관성을 유지할 수 있는 여러 방안이 도출되었습니다.

## 3. 대응방안
 ### (1) 패턴
1) 2PC(two-Phase Commit)
-  동작 방식 : 2단계의 Phase로 진행되는 방식으로 분리된 DB에 커밋이 가능한지 확인하는 단계(Phase 1: Prepare) , 커밋하는 단계(Phase 2: Commit)로 나누어 작동하는 방식으로 하나라도 Phase1에서 커밋이 불가능하다는 응답이 올경우
모두 롤백하는 방식
  - 장점
    - 강한 일관성을 가진다.
    - 부분 실패 시나리오가 발생하지 않는다.
  - 단점 
    - 모든 도메인 DB가 준비완료할때까지 대기를 하기때문에 성능저하의 문제가 있다.
    - 참여하는 도메인DB가 많을 수록 성능 저하는 더 급격하게 저하된다.
    - 각 도메인 디비를 제어하는 Coordinator가 장애가 발생할 경우 모든 도메인 DB가 대기상태로 멈추게 되는 큰 문제가 발생한다.
    -> 성능 저하의 문제가 매우 크고, 비효율 적이므로 해당 방식은 대규모 서비스에서 적용하기 어렵다는 문제가 있습니다.  
2) SAGA패턴
- Choreography 방식
  -  각 서비스가 이벤트를 발행하고 구독하며 자율적으로 동작하는 방식입니다.
  -  이벤트 체이닝 방식으로 프로세스에 포함되어있는 도메인 서비스간 단방향으로 구독하고 발행합니다 
  - 순수 Choreography방식은 1개의 이벤트당 1개의 리스너로 연결되어있는 구조입니다.
  - 하나의 이벤트에 여러 리스너가 동시에 구독하고 있는 구조또한 존재합니다. 중요한 비즈니스 로직과 부가기능을 분리하기 위해 사용 됩니다. (ex. 주문 프로세스 종료 후 성공 이벤트 > 알림 리스너/메일 리스너/통계 리스너가 처리) 
  -  동작 방식 (주문 생성 > 재고 차감 > 결제 처리)
     - 성공 시나리오
     ```
      주문 생성 후 주문 완료 이벤트 발행
                 ↓
      주문 완료 이벤트를 구독하는 재고 서비스에서 재고를 차감하고 이벤트 발행
                 ↓
      재고 차감 이벤트를 구독하는 결제 서비스에서 결제 처리하고 프로세스 완료
     ```
     - 실패 시나리오
     ```
      주문 생성 후 주문 완료 이벤트 발행 
                    ↓
      주문 완료 이벤트를 구독하는 재고 서비스에서 재고를 차감하고 이벤트 발행
                    ↓
      결제 서비스에서 실패 후 결제 실패 이벤트 발행 
                    ↓
      결제 실패 이벤트를 구독하는 재고서비스에서 재고를 증가 시키고 이벤트 발행 
                    ↓
      재고 증가 이벤트를 구독하는 주문 서비스에서 주문 취소
     ```
- **msa 아키텍처에서의 Choreography 구현** :
  - 이벤트를 전달할 메세지 브로커(kafka 등)를 두고 전달하는 방식으로 구현 합니다.
  - Order도메인에서 주문 저장 후 카프카 이벤트 발행 > 해당 이벤트를 구독하는 product 도메인에서 재고 차감 후 카프카 이벤트 발행 > ... 과 같은 방식으로 중간에 메시지 브로커 서버를 두고 수행합니다.
- Orchestration 방식
  - 중앙에서 제어하는 오케스트레이터를 두고, 각 도메인을 호출하여 조율하는 방식
  - 흐름 파악이 쉽다는 장점이 있다.
  -  동작 방식 (주문 생성 > 재고 차감 > 결제 처리)
     -  성공 시나리오
     ```
      주문 서비스 호출
            ↓
      재고 서비스 호출
            ↓
      결제 서비스 호출
     ```
     - 실패 시나리오 
     ```
     주문 서비스 호출
           ↓
     재고 서비스 호출
           ↓
     결제 서비스 호출 실패 
           ↓
     오케스트레이터에서 보상 트랜잭션 실행
     ```
  - **msa 아키텍처에서의 Orchestration 구현** : 
    - Orchestrator 서버를 중간에 두고 rest api 동기 호출을 통해 구현
    - Orchestrator가 명령을 발행하고 결과 이벤트를 구독 하는 방식 
      - 성공 시나리오
        ```
        Orchestrator : 주문 생성 명령 발행
            ↓
        주문 서비스 : 주문 저장 후 , Orchestrator 에게 완료 이벤트 발행
            ↓
        Orchestrator : 상태 변경 후 재고 차감 명령 발행  
            ↓
        재고 서비스:  재고 차감 후 완료 이벤트 발행
            ↓
        Orchestrator : 상태 변경 후 결제 명령 발행
            ↓
        결제 서비스 : 결제 처리 후 완료 이벤트 발행
            ↓
        Orchestrator : 상태 업데이트 
        ``` 
      - 실패 시나리오
       ```
        Orchestrator : 주문 생성 명령 발행
                     ↓
        주문 서비스 : 주문 저장 후 , Orchestrator 에게 완료 이벤트 발행
                     ↓
        Orchestrator : 상태 변경 후 재고 차감 명령 발행  
                     ↓
        재고 서비스 :  재고 차감 후 완료 이벤트 발행
                     ↓
        Orchestrator : 상태 변경 후 결제 명령 발행
                     ↓
        결제 서비스 : 결제 실패 후 실패 이벤트 발행
                     ↓
        Orchestrator : 상태 업데이트 재고 복구 명령 발행  
                     ↓  
        재고 서비스 : 재고 복구 후 완료 이벤트 발행
                     ↓  
        Orchestrator : 상태 업데이트 후 주문 취소 명령 발행
                     ↓  
        주문 서비스 : 주문 취소 후 완료 이벤트 발행
                     ↓  
        Orchestrator : 상태 업데이트 후 종료
       ```
### (2) 채택할 방식
- Choreography + Outbox Pattern 
- 사유 :
  - 실패 및 성공 시나리오를 순서대로 나열해 보았을 때, Orchestrator방식은 중앙 관리가 쉽다는 이점이 있지만  Orchestrator를 거쳐서 진행하는 것이 조금 비효율 적이라는 생각이 들었습니다. 
  - 서비스 간 독립성을 최대한 유지되는 이점이 있습니다.
  - Outbox 테이블 추가를 통해 이벤트 유실을 막고, 도중에 중단되어도 재시도를 처리하기 용이합니다.`
- 구현 방식
  - 메시지 브로커: Kafka
  - 트랜잭션 보장: Outbox Pattern을 사용하여 보완
  - out box 테이블 발행 방법 : Debezium 사용
  - 보상 트랜잭션: 역방향 이벤트 체이닝
 - 동작 방식 (주문 생성 > 재고 차감 > 결제 처리)
   ```
     주문 서비스 : 주문 생성 >  이벤트 발행 >  아웃박스 테이블에 저장  > Debezium이 감지 하여 카프카 자동 발행 
               ↓  
     재고 서비스 : 재고 차감 >  이벤트 발행 >  아웃박스 테이블에  > Debezium이 감지 하여 카프카 자동 발행 
               ↓ 
     결제 서비스 : 결제 > 이벤트 발행 > Debezium이 감지 하여 카프카 자동 발행           
   ```

## 4. 주의 사항
 - 보상 트랜잭션 구현 시, 같은 보상 요청을 여러번 수행해도 한번만 수행하도록 멱등성을 보장해야 합니다.
 - 외부 API호출 같은 보상 불가능한 작업은 보상 트랜잭션으로 해결 할 수 없기 때문에 다르게 처리해야합니다.
 - 타임아웃 및 장애로 인한 보상 전략 실패시 재시도 정책에 대한 프로세스도 구성해야 합니다. 

## 5. 결론 및 느낀점
- 이번 과제에서 핵심 로직과 부가기능을 분리하기 위해 이벤트를 사용해보았습니다. 1개의 이벤트에 여러 리스너가 구독하는 혼합 Choreography방식으로 구현해 보았는데요.
처음에는 이벤트 동작 구조에 익숙하지 않아 헷갈리는 부분도 있었으나 관심사를 분리할 수 있다는 점, 이후 다른 부가로직이 추가 되더라도 기존의 핵심로직은 영향을 받지 않고 추가 할 수 있다는
장점이 있다는 것 또한 배우게 되었습니다.

- 개인적으로는 실무에서 한 서비스에 너무나 많은 서비스가 의존을 해서 결합도가 강한 코드에 대해 많이 회의적이었는데, 이번 과제를 통해 조금 더 좋은 방안에 대해 모색할 수 있는 계기가 된 것 같습니다.
